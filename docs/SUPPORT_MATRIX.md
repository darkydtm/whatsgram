# Whatsgram directional support matrix

Research status: completed with documented limitations. Exact dependency versions are selected for the project; operational policies below distinguish accepted defaults from research proposals. This is phase 1 API evidence, not a claim that the bridge is implemented.

## Evidence boundary and terminology

- N = native API operation documented in the selected library or official platform documentation. This confirms an API contract, not successful use against a live account.
- P = protocol/source capability only, including generic receive envelopes, protobuf fields and generic SendMessage transport. Server acceptance, permissions or exact semantics remain unverified. A field is never sufficient evidence for N.
- E = explicit emulation/fallback, preserving linkage and naming the limitation.
- U = unavailable in the ordinary Telegram forum-supergroup Bot API model or not established in the selected WhatsApp API. Unknown is not a reason to discard an accepted event.
- NI = not implemented. Every bridge row below is NI at this research handoff, including rows whose endpoint APIs are N. Intended implementation phases appear separately.
- Local compatibility: real database/sql + modernc + whatsmeow sqlstore probe passed with CGO_ENABLED=0. It is not messaging integration.
- Remote Telegram/WhatsApp integration: NOT RUN. No test accounts, sessions or permission supplied. Native/source-supported operations still need permitted live acceptance tests.
- WhatsApp identity is the linked account. Telegram identity is the bot. Sender labels, textual reaction/vote summaries and forwarding annotations are attribution, never impersonation.

Telegram incoming evidence T:update + T:message means https://core.telegram.org/bots/api#update and #message plus G01. It does not imply all user messages are observable: bot must be group admin or privacy mode disabled. Bots do not receive other bots' messages under the official FAQ (https://core.telegram.org/bots/faq#what-messages-will-my-bot-get). Anonymous sender_chat messages are rejected as control inputs unless explicitly mapped and authorized; never infer a user ID from a display name.

## Telegram method and transfer limits verified against API 10.3

- Cloud getFile downloads up to 20 MB (T:getfile); source S03 guard is 20 << 20 bytes. Returned link valid at least one hour; preserve filename/MIME from input because getFile may not preserve them.
- Cloud multipart: photos up to 10 MB; other files up to 50 MB (T:sending-files). sendPhoto additionally sum(width,height) <=10000 and aspect ratio <=20 (T:sendphoto).
- Cloud URL send: photos 5 MB, other content 20 MB (T:sending-files). sendDocument URL documented for PDF/ZIP only. sendVoice by URL must be audio/ogg <=1 MB for voice representation. Do not apply multipart limits to URL or file_id mode indiscriminately.
- Existing Telegram file_id resend has no reupload size limit; file_id is bot-specific, cannot change media type or be transferred between bots (T:sending-files).
- Local Bot API with local mode permits upload up to 2000 MB and download without Bot API size limit, and local path/file URI upload (T:using-a-local-bot-api-server; server README https://github.com/tdlib/telegram-bot-api). This does not bypass media-type-specific validation, photo dimensions, target WA limits or bridge resource caps. Set endpoint with G04 WithServerURL.
- Selected go-telegram/bot raw_request.go:28-55 buffers the entire multipart upload into memory. Do not promise bounded-memory 2000 MB uploads using InputFileUpload. Minimal policy: prefer allowed local-server file path input for large files, otherwise enforce configured per-file and aggregate-inflight memory cap; streaming transport would be a separate accepted change, not an assumed library feature.
- Video MPEG4; audio MP3/M4A; voice OGG/Opus, MP3/M4A; GIF or silent H.264/MP4 animation (corresponding T send methods). Video notes MPEG4 <=1 minute; no URL input. Animated stickers .TGS, video stickers .WEBM; animated/video stickers cannot be sent by URL (T:sendsticker).
- Official sticker requirements https://core.telegram.org/stickers#animated-stickers-and-emoji: TGS canvas 512x512, <=3 seconds, looped, <=64 KB, 60 FPS. #video-stickers-and-emoji: WebM/VP9, one side 512 and other <=512, <=3 seconds, <=30 FPS, <=256 KB, no audio. #static-stickers-and-emoji: PNG/WebP, one side 512 and other <=512. Bot API sendSticker documents WebP static input, so normalize to WebP. Ordinary 50 MB upload limit is not a sticker limit. WA media/text maximums remain unresolved and must be checked before phase 4 native acceptance; configured conservative caps are policy, not platform proof.
- sendMediaGroup: 2-10 items; audio/doc albums homogeneous; per-part Message IDs returned; editMessageMedia constrains album type. TG text 4096, captions 1024, forum names 1-128. Split by semantic text/entities, not bytes, and maintain complete part mappings.

## Access, event persistence and recovery policy proposals

1. Admission: require exact Telegram meta-group ID and authorized numeric sender ID for sends and commands. Operator-only control operations, ordinary sender can send only own permitted content. Reject anonymous sender_chat control unless separately configured. WhatsApp messages/events are data only, never commands. Slash commands are not bridged as chat text. Reactions/votes need policy authorization too, not just message admission.
2. Accepted initial multi-user account policy: all allowed Telegram users are authorized operators for explicit management commands; ordinary edits/deletes remain restricted to their own linked originals unless an explicit audited override is invoked and platform permissions permit. The numerically smallest allowlisted Telegram user ID is the designated reaction/poll-vote driver for the ONE linked WA account. Other users' intents use a visible rejection or labeled textual fallback, never a second fictional WA identity. Revoking/changing the driver updates the effective policy at restart and must be diagnosed. A verified mention link is not permission to impersonate reaction/vote authors. Do not infer cross-user role authorization from display names.
3. Topic policy: store discovered -> creating -> active plus closed/missing/uncertain/blocked. Closed pauses with operator notification; no reopen on every incoming message. Permanent 400 target/method/type error or 403 rights loss quarantines operation; retry only explicit permission repair or remap. CreateForumTopic success/save failure is uncertain, not safely replayable; wait for persisted matching service observation or operator-assisted bind. Don't claim topic idempotency by title alone.
4. Bootstrap: GetJoinedGroups + history conversation JIDs + new event JIDs + verified contact display cache. Contacts are not proof of an existing conversation. Mapping discovery is idempotent on canonical JID and topic generation, topic creation is not exactly-once. Default no historical messages copied; optional bounded import from supplied history/on-demand pages (50 recommended per W19), never guaranteed all chats/full history. Record partial bootstrap and lost/recovery-unavailable coverage, don't silently declare complete.
5. Telegram durable admission: stock Bot.Start updates lastUpdateID before enqueue (G03), and stock WebhookHandler returns without DB commit. Use project-controlled narrow getUpdates HTTP poller, decoding selected client models and storing entire batch plus offset transactionally before next offset request, or project-controlled webhook admission returning 2xx only after commit. Keep go-telegram/bot for send APIs. Raw getUpdates client method is unexported. Handle unknown/malformed-but-identifiable input as private quarantine and visible diagnostic before offset advancement, not raw-payload logging. Updates retained upstream <=24h (T:getting-updates), not unlimited recovery.
6. WA durable admission: configure SynchronousAck=true + EnableDecryptedEventBuffer=true; register AddEventHandlerWithSuccessStatus; synchronously commit inbox before return true, false on persistence error. Do not panic: dispatchEvent recovers and does not reliably turn panic into failed-handler status. Retry with bounded backoff and reconnect if saturation persists. Ordinary encrypted messages preserve decrypt-state+plaintext buffer across admission failure (W20/W22); this does not make all notifications/history exactly-once. History protocol receipts are independently sent (message.go:899-906), app-state notifications spawn fetch goroutines, presence has no ACK equivalent. ManualHistorySyncDownload=true and DisableManualHistorySyncReceipt=true are proposed for history admission: persist notification first, fetch/persist then send protocol receipt, validate this path before claiming it. Document state-change replay gaps and reconcile supported group/app state after reconnect; cannot promise server re-delivery of every event.
7. WA outgoing IDs: allocate Client.GenerateMessageID once, persist outbox payload and SendRequestExtra.ID before network. Preserve same ID/payload across retries; echo table matches exact account+canonical chat+ID+operation/version, never blanket IsFromMe. This gives an API-level retry/correlation key, not proven server exactly-once or arbitrary sent-message lookup. ACK indicates server acceptance, not human rendering. Timeout/post-send crash = uncertain; reconcile against actual observed exact ID/history if available, bounded same-ID retry only explicit policy, then operator notice. Record a risk if dedup acceptance is unverified.
8. TG outgoing creates have no caller idempotency key in documented send methods. Timeout, failed body decode/read after possible acceptance, crash after response before result commit, or topic-create ambiguity = uncertain. No automatic fresh send that is falsely described as exactly-once. Default pause automatic retry of uncertain creates; expose /retry with duplicate-risk warning or /bind known message/topic ID with checked scope. TG bot's own sends cannot be assumed to echo through updates; stock API cannot search arbitrary topic history. Mutations may be retryable by desired-state only after rights/ownership/version checks.
9. Dependent operations wait for mapping, bounded by configurable deadline (proposed 120 seconds), with reconnect/history request if available. On expiry, emit linked unresolved-reference notice; never discard reaction/edit/revoke silently. Early revoke creates tombstone placeholder even if original arrives later; late create cannot resurrect. Source ordering uses TG per-message edit_date then within-current-stream update ID; WA protocol edit/reaction/vote sender timestamps plus raw event identity, retaining raw envelope before ParseWebMessage rewrites target ID. Equal WA versions with different payload are ambiguous: quarantine conflict + operator-visible notice, not arbitrary newer-by-arrival assertion. Wall-clock alone across two sources is insufficient.
10. Durable queues: pending/leased/retry/sending/uncertain/blocked/dead; fenced lease token + deadline, per-chat serialization, transactional state+outbox creation. Expired leased/sending create becomes uncertain if send_started_at exists. Retry only explicit transient classes with exponential backoff+jitter, obey TG retry_after. Permanent failures produce one deduplicated fallback/diagnostic. Operator actions are audited without message bodies/secrets in logs. Configured queue count/bytes cap stops admission safely rather than acknowledging dropped data.
11. Restart timers: absolute source-based deadlines, never restart-relative. Tombstone/keep/version guards checked inside transaction before deleting parts. Expiry jobs must attempt every part individually and track incomplete deletion. 7d/90d TG mirrors cannot be promised to disappear at deadline under <48h delete limit; labels are not deletion. Stored payload/media retention must expire too unless minimal tombstone metadata needed for dedupe. Backup copies are an explicit privacy limitation.
